分布式事务

在单体应用中，Spring 加上 @Transactional 注解，数据库就会保证：要么全做，要么全不做。

但拆分成微服务后，跨服务的调用不再受数据库事务保护。

以电商系统为例，用户点击“下单”按钮，后台会发生两个动作：

  1. 订单服务：在订单库创建一条订单记录。
  2. 库存服务：在库存库扣减一个商品库存。

在微服务架构下，这是两个跨网络的独立调用。订单创建成功了但库存扣减超时，或者库存扣减成功了但订单服务挂了——无论哪种情况，数据都会出现不一致：多卖了货，或者少记了账。

这就是分布式事务要解决的核心问题：如何跨越网络的不确定性，维持数据的一致性。

理论基石

在看具体方案之前，先理解单体事务的保证机制，再看分布式环境下这些保证为什么会失效。

回顾：ACID 与分布式困境

单体应用中，数据库事务依赖 ACID 四大属性来保证数据安全：

  • A (Atomicity，原子性)：事务中的操作要么全部成功，要么全部回滚，不存在中间状态。数据库通过 undo log 实现——如果事务失败，利用日志将数据还原到事务前的状态。
  • C (Consistency，一致性)：事务执行前后，数据始终满足所有约束条件（如外键、唯一索引、业务规则）。这是应用层和数据库层共同保证的结果。
  • I (Isolation，隔离性)：多个并发事务互不干扰，每个事务看到的都是”独立”的数据库。数据库通过锁机制或多版本并发控制（MVCC）实现不同级别的隔离（读未提交、读已提交、可重复读、串行化）。
  • D (Durability，持久性)：事务一旦提交，数据就永久保存，即使系统崩溃也不丢失。数据库通过 redo log 实现——提交时先写日志，崩溃恢复时重放日志。

Spring 的 @Transactional 注解本质上是把这四个保证委托给了数据库连接（Connection）的 commit()/rollback() 机制。但拆成微服务后，订单服务和库存服务各自有独立的数据库连接，没有一个统一的 commit() 能同时覆盖两个库——ACID 的原子性在跨网络场景下失效了。

这就是分布式事务需要解决的根本矛盾：单机 ACID 无法跨网络延伸，但业务又需要跨服务的数据一致性。

为了理解各类分布式事务方案的取舍，我们需要先看清分布式系统的理论边界：CAP 定理给出了约束条件，BASE 理论指出了工程策略，而 2PC 则是最早的强一致性尝试。

CAP 定理：不得不做的选择题

该理论最初由 Eric Brewer 在 2000 年 PODC 会议上提出猜想，后由 Seth Gilbert 和 Nancy Lynch 在 2002 年通过形式化证明确立。

定理内容为：在一个分布式数据存储系统中，一致性、可用性、分区容错性 这三个基本要素，最多只能同时满足其中的两项。由于网络不可靠是客观事实，P 是必须满足的前提，因此实际的选择是：当网络分区发生时，选择 CP（强一致，但可能不可用）还是 AP（高可用，但允许暂时不一致）。

  • C (C onsistency)：一致性，所有节点在同一时间看到相同的数据。
  • A (A vailability)：可用性，系统总能响应请求，即使部分节点挂了。
  • P (P artition tolerance)：分区容错性，即网络分区导致节点间通信中断时，系统仍能持续运行。

因此真正的抉择在于 CP 与 AP 之间的权衡。

CP 架构：一致性优先

当网络分区发生时，CP 架构会选择牺牲可用性来换取数据准确性。具体来说，如果部分节点因为网络问题无法与其他节点同步，系统会主动拒绝服务或阻塞请求，直到网络恢复并达成共识——代价就是在分区期间，部分或全部功能不可用。

这种”宁可不服务，也不能给错误数据”的设计，依赖的是共识算法（如 Paxos、Raft、Zab）和多数派机制（Quorum）——以 Raft 为例，一次写入必须获得超过半数节点的确认才算成功，这从机制上杜绝了脑裂和数据冲突。

典型系统包括 ZooKeeper / Etcd（分布式协调，Leader 选举期间写入不可用，但 Follower 仍可提供读服务，选举通常在几百毫秒内完成）、HBase（每个 Region 由单一 RegionServer 提供写入服务（通过 ZooKeeper 选主），底层 HDFS 采用同步多副本写入，从架构上保证了强一致性。）。这类架构常见于金融交易、库存扣减、分布式锁等对数据准确性要求极高的场景。

AP 架构：可用性优先

与 CP 相反，AP 架构在分区发生时优先保证业务不中断。即使节点之间失去联系，每个节点仍可独立响应请求，返回本地已有的数据——哪怕这份数据可能不是最新的。等到网络恢复后，系统再通过后台机制进行数据合并与冲突解决。代价是不同节点在短期内可能持有不同版本的数据。

实现这种”先响应、后对齐”的机制包括：Gossip 协议（节点间随机通信传播状态变化）、向量时钟与 CRDTs 等冲突解决策略，以及 Read Repair、Hinted Handoff 等反熵机制来逐步收敛数据。

典型系统如 Cassandra / DynamoDB（写入即可返回，后台异步同步）和服务发现组件 Eureka（优先保证客户端能拿到服务列表，哪怕列表里混着已下线的节点）。社交点赞、商品评论、DNS 解析这类对短暂不一致容忍度较高的业务，天然适合 AP 架构。

PACELC 理论

由 Daniel Abadi 提出，填补了 CAP 理论中“无分区时如何权衡”的空白。

P (Partition)：如果有网络分区，必须在 A（可用性）和 C（一致性）之间选择。
E (Else)：如果没有网络分区，必须在 L（Latency，延迟）和 C（一致性）之间选择。

深层含义：强一致性通常意味着需要等待更多节点的确认，这必然增加延迟。追求极致低延迟，往往需要放宽一致性要求。

BASE 理论：放弃强一致性

CAP 定理给出了约束条件，而 BASE 理论则是在该约束下的工程策略——既然分区不可避为了追求互联网应用的高可用，我们往往退而求其次，遵循 BASE 理论：

  • BA (Basically Available)：基本可用，允许服务降级。具体表现包括：高峰期返回缓存数据而非实时数据、非核心功能降级到只读模式、限流后返回”请稍后重试”而非直接超时。核心是”有响应比没响应好”。
  • S (Soft state)：软状态，允许系统在没有新外部输入的情况下自行变更状态（如后台异步复制导致数据暂时不一致）。业务上类似”支付中”这种待定状态，也是系统容忍中间态的体现——系统不需要在每一刻都处于一个确定状态。
  • E (Eventually consistent)：最终一致性，经过一段时间数据终变一致。”一段时间”可能是毫秒级（同机房同步）也可能是分钟级（跨地域复制），但系统保证在没有新写入的情况下，所有副本最终会收敛到相同值。

BASE 与 ACID 的本质区别在于：ACID 要求”事务结束时数据一定正确”，BASE 允许”中间状态可见，但最终会正确”。后续讨论的 Saga、TCC 补偿、消息队列最终一致性等方案，都是 BASE 理论在不同场景下的具体实践。

不过，BASE 并非万能。在金融交易、库存扣减等场景下，”最终一致”意味着”短暂不一致”，这个窗口期内可能造成资金损失。因此业界一直在探索分布式强一致性方案——2PC（两阶段提交）是最早的尝试，也是后续所有方案的起点。

2PC 与 3PC：强一致性的代价

2PC (Two-Phase Commit) 由 Jim Gray 在 1978 年提出，是一种试图在分布式环境实现严格原子性的协议。后续 X/Open 组织将其标准化为 XA 规范（X/Open XA），Java 生态中的 JTA（Java Transaction API）和 Atomikos、Narayana 等事务管理器都基于 XA 实现。

2PC 的完整流程：

  • 阶段 1 (Prepare)：协调者向所有参与者发送 Prepare 请求。参与者收到后：(1) 执行本地事务的 SQL，但不提交；(2) 将 undo log 和 redo log 写入磁盘；(3) 锁定相关资源行；(4) 向协调者回复 Yes 或 No。
  • 阶段 2 (Commit/Rollback)：协调者收集所有回复。
    • 全部 Yes → 发送 Commit 指令，所有参与者正式提交，释放锁。
    • 任一 No（或超时未回复）→ 发送 Rollback 指令，所有参与者利用 undo log 回滚，释放锁。

2PC 的三个严重问题：

  • 同步阻塞：所有参与者在 Prepare 阶段持锁等待，必须等到最慢的那个回复才能进入阶段 2。在 N 个参与者的场景下，整体延迟取决于最慢的那个——锁的时间 = 网络往返 + 最慢参与者的本地事务耗时。
  • 协调者单点故障（阻塞风险）：如果协调者在阶段 2 的 Commit 指令发出前崩溃，参与者会无限期处于 READY 状态——已经锁了资源、写了日志，但不知道该提交还是回滚。只能被动等待协调者恢复，期间资源被锁死。
  • 数据不一致风险：如果 Commit 指令只发到了部分参与者（网络分区），就会出现一部分提交、一部分未提交的不一致状态。

3PC 的改进与局限：

为了解决 2PC 的阻塞问题，3PC (Three-Phase Commit) 引入了 PreCommit 阶段和超时机制：

  • CanCommit：协调者询问参与者”能否提交？”（轻量级探查，不锁资源）。
  • PreCommit：全部 Yes 后，协调者发送 PreCommit，参与者此时才真正执行 Prepare（写日志、锁资源）。
  • DoCommit：协调者发送最终 Commit 指令。

关键改进：如果参与者在 PreCommit 阶段后长时间收不到 DoCommit 指令（超时），会自动提交——因为既然已经进入了 PreCommit，说明所有参与者都投了 Yes，大概率可以安全提交。

但 3PC 也有致命缺陷：在网络分区场景下，”超时自动提交”可能导致部分参与者提交、部分参与者回滚，造成脑裂和数据不一致。因此 3PC 在实际工程中几乎没有被直接采用，但它的设计思想（减少阻塞、引入超时）影响了后续的 TCC 和 Saga 等方案。

PACELC 理论

由 Daniel Abadi 提出，填补了 CAP 理论中”无分区时如何权衡”的空白。

P (Partition)：如果有网络分区，必须在 A（可用性）和 C（一致性）之间选择。
E (Else)：如果没有网络分区，必须在 L（Latency，延迟）和 C（一致性）之间选择。

深层含义：强一致性通常意味着需要等待更多节点的确认，这必然增加延迟。追求极致低延迟，往往需要放宽一致性要求。后续讨论的 Saga、TCC、消息队列等方案，本质都是在一致性、可用性、延迟之间做不同权衡——PACELC 提供了理解这些权衡的框架。

主流解决方案

Seata (Simple Extensible Autonomous Transaction Architecture) 是阿里巴巴开源的分布式事务解决方案，目标是让分布式事务的使用像本地事务一样简单。

Seata 的架构由三个核心组件组成：

  • TC (Transaction Coordinator)：事务协调器，独立部署的服务端，负责管理全局事务的生命周期（开启、提交、回滚），维护全局锁。
  • TM (Transaction Manager)：事务管理器，嵌入业务应用中，负责发起全局事务（通过 @GlobalTransactional 注解标记入口方法）。
  • RM (Resource Manager)：资源管理器，嵌入业务应用中，负责管理分支事务（如数据库连接），向 TC 注册分支事务并报告执行结果。

一次典型的分布式事务流程：TM 发起全局事务 → TC 分配全局事务 ID（XID）→ 各 RM 执行本地事务并注册分支 → TC 根据各分支结果决定全局提交或回滚 → TM 结束全局事务。

Seata AT 模式

AT 模式是这一目标的最直接体现：不需要修改业务代码，只需要加一个注解。Seata 会利用代理机制（通过 DataSourceProxy 代理数据源），拦截你的 SQL，自动记录”修改前的数据”和”修改后的数据”到 undo_log 表中。如果所有服务都成功，它就清理掉这些记录；如果有服务失败，它就利用这些记录生成反向补偿 SQL 把数据还原。

undo_log 的工作原理：

每个需要 AT 模式的业务数据库中，都需要建一张 undo_log 表（Seata 提供建表脚本）。表的核心字段包括：branch_id（分支事务 ID）、xid（全局事务 ID）、rollback_info（序列化后的前后镜像数据）。流程如下：

  1. 一阶段：Seata 拦截 SQL，执行前记录 Before Image，执行后记录 After Image，与业务 SQL 在同一个本地事务中写入 undo_log。
  2. 二阶段提交：全局事务成功，异步删除 undo_log 记录（批量清理，不影响主流程性能）。
  3. 二阶段回滚：全局事务失败，取出 Before Image，生成反向 SQL（如原操作是 UPDATE SET stock=90，反向 SQL 为 UPDATE SET stock=100），执行回滚后删除 undo_log。

AT 模式是典型的低门槛方案，但它有一个隐患：脏写。

如果有一个非 Seata 管理的后台脚本，直接去修改了数据库，会发生什么？

  1. 事务 A 修改库存，提交本地事务（释放了数据库行锁）。
  2. 外部脚本修改库存。
  3. 事务 A 收到回滚指令，根据 Before Image (100) 强行回滚：SET stock = 100。
  4. 结果：外部脚本修改的 80 被覆盖丢失了。

为了解决这个问题，Seata 引入了全局锁——在二阶段提交/回滚完成前，该记录被 Seata 的协调者（TC）逻辑锁定。全局锁的实现细节：

  • 锁粒度：行级锁，存储在 TC 端（内存 + 持久化到 DB/Redis）。
  • 锁获取：一阶段提交前，RM 向 TC 申请全局锁。如果该行已被其他全局事务锁定，当前事务会等待（可配置超时时间，默认 30s，超时后抛异常回滚）。
  • 锁冲突策略：默认等待重试，也支持快速失败（不等待直接回滚）。
  • 与本地锁的关系：全局锁是 TC 端的逻辑锁，与数据库的行锁互不干扰。本地事务提交后数据库行锁即释放，但全局锁要到二阶段完成后才释放。

但全局锁在热点数据场景下会成为瓶颈：成千上万的请求同时抢夺同一行记录，不仅拖低吞吐量，还容易引发锁等待超时。

AT 适合并发量适中、非热点数据、追求开发效率的中后台业务。

XA 模式

XA 是 X/Open 组织制定的分布式事务接口标准，它采用 2PC 作为提交协议。因此，XA 模式本质上是 2PC 在数据库层面的标准化实现——协调者与参与者之间的交互由数据库原生支持，而非像 AT 模式那样由 Seata 在应用层模拟。

  • 一阶段（Prepare）：业务代码执行 SQL，但在提交时，Seata 的事务管理器（TM）会告诉数据库：”先别真提交，把资源锁死，数据写入日志，进入’准备好’的状态”。此时，数据库会锁定这一行数据，任何人都动不了。
  • 二阶段（Commit / Rollback）：Seata 收集所有服务的状态。
    • 全成功：通知数据库”正式提交”，数据库释放锁，数据生效。
    • 有失败：通知数据库”回滚”，数据库利用自身的日志恢复，释放锁。

优点：

  1. 强一致性：由数据库保证，在合适的隔离级别（如 SERIALIZABLE）下没有脏读，没有中间状态。
  2. SQL 支持度好：AT 模式解析复杂 SQL（如存储过程、复杂连接）可能会失败，但 XA 是数据库原生的，SQL 兼容性与数据库引擎一致。
  3. 无侵入：不需要像 AT 那样建 undo_log 表。

缺点：

  1. 性能差：数据库锁要持有到第二阶段结束，锁的时间长，并发度低。
  2. 单点风险：这是经典 2PC 的固有问题——如果协调者崩溃，参与者无法自行决定。但在 Seata 的 XA 模式中，TC 可以高可用部署（集群模式），且数据库本身有锁等待超时机制（如 MySQL 的 innodb_lock_wait_timeout），不会无限期死锁。此外，数据库支持 xa recover 命令可恢复处于 PREPARED 状态的事务。

过去互联网公司不用 XA 是因为性能差。但随着云原生数据库（如阿里云 PolarDB）和高速网络的普及，XA 的性能损耗被大幅降低——PolarDB 的共享存储架构减少了 2PC 的网络往返次数，RDMA 高速网络将 Prepare-Commit 的延迟从毫秒级降到微秒级。对于非高并发、但数据极其重要的系统（如内部 ERP、财务系统），XA 是稳妥的选择。

Seata TCC 模式

AT 模式因为要加全局锁，性能有上限。TCC 的思路是把锁的粒度从数据库层面移交到业务逻辑层面。

类比：买房交定金

  • Try (定金)：你不用付全款，先付 5 万定金。房产中介把房子“锁”住（预留），别人买不了。
  • Confirm (交房)：你凑齐了首付，正式过户。
  • Cancel (退定)：你反悔了，中介把房子释放出来卖给别人，定金退回。

TCC 灵活性高，但复杂性完全转嫁给了业务方。在分布式网络环境中，必须在代码中处理以下三种异常，否则会导致资金损失。这些异常的防护逻辑需要用一张事务状态表来记录每个事务 ID 的执行状态：

  1. 空回滚

    • 场景：Try 请求因为网络丢包，根本没发到库存服务。但协调器（TC）认为失败了，触发了 Cancel。
    • 后果：Cancel 执行了”退钱/释放库存”的操作。如果没做防护，会导致库存凭空增加。
    • 对策：Cancel 执行时，先查事务状态表——如果没有该 XID 的 Try 记录，说明 Try 未执行过，直接返回成功，不做任何业务操作。

  2. 幂等

    • 场景：网络抖动，TC 以为 Confirm 超时了，重发了一次 Confirm。
    • 后果：库存被扣了两次。
    • 对策：Confirm/Cancel 执行前，先查事务状态表——如果该 XID 已经处理过（状态为 CONFIRMED 或 CANCELLED），直接返回成功，不重复执行。

  3. 悬挂

    • 场景：网络极度拥堵。Cancel 比 Try 先到了。Cancel 发现没 Try 过，直接返回成功（空回滚）。随后，迟到的 Try 到了，并执行成功。
    • 后果：资源被 Try 冻结了，但永远不会被 Confirm 或 Cancel，成为无法回收的资源。
    • 对策：Try 执行时，先查事务状态表——如果该 XID 已经存在 Cancel 记录，说明 Cancel 已先到（悬挂），Try 应拒绝执行。

Seata Saga 模式

有些业务流程很长，既不能像 AT 模式那样长时间锁表，也不能像 TCC 那样要求每个服务都改造代码。

你要预订一次欧洲旅行，流程是：订机票 订酒店 租车。这个流程涉及三个不同的供应商，甚至可能需要人工审核，整个过程可能持续几分钟甚至几小时。

  • 如果用 AT/TCC：从订机票开始，数据库就被锁住了。直到租车成功，机票的锁才释放。这期间，别人无法买这张票。

核心定义：Saga 模式把一个大事务拆分成多个各自独立提交的本地短事务。就像接力赛：

  • 第一棒（机票）跑完，立刻提交，释放锁。
  • 第二棒（酒店）跑完，立刻提交。
  • 如果第三棒（租车）摔倒了，Saga 协调器会负责往回跑：退酒店（补偿）、退机票（补偿）。

需要注意的是，补偿操作本身也可能失败（如退款 API 超时）。因此所有补偿事务必须设计为可重试且幂等的，Saga 协调器需要具备自动重试机制。

Saga 的核心在于定义”如何前进”和”如何后退”，开发者需要通过 JSON 或代码定义一个状态机。以 Seata Saga 为例，状态机定义如下：

补偿不等于撤销：补偿操作不一定能”撤销”原操作（已发送的短信无法撤回、已发货的包裹无法自动召回）。对于不可逆操作，通常的策略是”发放补偿”——例如取消订单后发放一张优惠券，而非试图撤回已发送的通知。这是 Saga 模式在设计时需要特别注意的约束。

Saga 的两种实现方式：

维度 协同式（Choreography） 编排式（Orchestration）
协调方式 去中心化，各服务通过事件驱动自行监听和响应 中心化，由编排器（状态机）统一调度
通信机制 消息队列（每个服务发布事件，其他服务订阅） 编排器直接调用各服务 API
优点 无单点故障，服务间松耦合 流程清晰可控，易于监控和调试
缺点 流程分散在各服务中，难以追踪和调试；服务间形成隐式依赖 编排器是单点（需高可用），服务与编排器耦合
适用场景 简单的 2-3 步流程 复杂的多步流程、需要人工审核的长流程

Seata 采用编排式（状态机驱动），因为编排式可以集中管理补偿逻辑和异常处理，更适合企业级复杂业务场景。

  • 正常情况（All Good）：BookFlight → BookHotel → RentCar → End
  • 异常情况（RentCar 失败）：BookFlight → BookHotel → RentCar(失败) → Catch → CancelCar → CancelHotel → CancelFlight

Saga 打破了 ACID 中的隔离性（Isolation）。因为每个子事务都是立即提交的，中间状态对外界可见，会引发脏读。

  1. 用户 A 订了最后一张机票（ 提交）。
  2. 用户 B 来查票，发现没票了（看见了 A 的提交）。
  3. 用户 A 后续的酒店预订失败了，触发补偿取消了机票（ 执行）。
  4. 结果：用户 B 刚才看到的是一个“无效”的状态，且因为这个状态放弃了购买。这就是 脏读。

为了解决这个问题，通常需要在业务层面引入语义锁（Semantic Lock）。比如在订机票时，不直接把票减掉，而是将状态改为 BOOKING_PENDING（预订中）；只有当整个 Saga 流程全部完成，才把状态改为 CONFIRMED。

语义锁的完整生命周期：

  1. 设置：第一步子事务执行时，将资源状态从 AVAILABLE 改为 BOOKING_PENDING。
  2. 释放（成功）：整个 Saga 流程全部完成，最后一步将状态从 BOOKING_PENDING 改为 CONFIRMED。
  3. 释放（失败）：任何一步失败触发补偿，将状态从 BOOKING_PENDING 改回 AVAILABLE。
  4. 超时清理：如果 Saga 流程卡住（如编排器崩溃），BOOKING_PENDING 状态会一直存在。需要一个定时任务扫描超时的 PENDING 记录（如超过 30 分钟），将其回滚为 AVAILABLE 或触发告警人工介入。
  5. 对查询的影响：查询接口需要过滤掉 PENDING 状态的资源——对外只展示 AVAILABLE 和 CONFIRMED，避免用户看到”已被占但可能回滚”的中间态。

Saga 适合业务流程长、跨机构或跨遗留系统的场景。

RocketMQ 事务消息

并不是所有业务都需要”同时成功”。比如用户支付成功后需要增加积分，如果积分服务挂了，用户通常能接受积分晚 10 秒到账。

这就不需要强一致性事务，而是最终一致性。核心思想是：只要本地事务成功了，就保证消息一定能发出去；只要消息发出去了，消费者最终一定能收到。

普通的 MQ 发送消息是不可靠的：可能消息发出去了，本地数据库回滚了；或者本地数据库提交了，消息发失败了。RocketMQ 引入了 Half Message（半消息） 来解决原子性问题。

核心步骤：

  1. 发送半消息：生产者发一条消息给 MQ，MQ 收到了但不给消费者看（Pending 状态）。
  2. 执行本地事务：生产者执行具体的业务（如：更新订单状态）。
  3. Commit/Rollback：
    • 本地事务成功，通知 MQ “这条消息可以投递了”。
    • 本地事务失败，通知 MQ “把这条消息删了吧”。

RocketMQ 方案的关键在于处理”未决”状态。如果在执行本地事务后，服务器立刻断电，没来得及发 Commit 给 MQ，MQ 里的消息会一直是”半消息”状态。RocketMQ 会启动回查机制（Transaction Check Back），主动问生产者：”刚才那个事务 ID，你到底执行成功没？”生产者需要实现一个检查接口（例如查数据库订单表），确认事务状态并回复。

回查策略配置：

  • 回查间隔：由 Broker 配置（默认 60 秒），第一次回查在半消息发送后 60 秒触发。
  • 最大回查次数：默认 15 次。超过后消息会被丢弃（或进入死信队列，取决于 Broker 配置）。
  • 回查触发条件：(1) 本地事务执行后未发送 Commit/Rollback；(2) Commit/Rollback 发送失败（网络问题）；(3) 本地事务执行超时。

消费者端的可靠性保障：

消息到达消费者后，消费者消费失败怎么办？RocketMQ 提供了重试机制：

  • 消费重试：消费者返回 RECONSUME_LATER 或抛异常时，消息会进入重试队列，默认最多重试 16 次，重试间隔递增（10s、30s、1m、2m…2h）。
  • 死信队列（DLQ）：重试耗尽后消息进入死信队列，需要人工介入处理。
  • 幂等消费：由于消息可能被重复投递（网络抖动、重试），消费者必须实现幂等——通常用消息 ID 或业务唯一键做去重。

本地消息表模式（替代方案）：

如果不用 RocketMQ，也可以用本地消息表（Local Message Table）模式。原理一样：在同一个数据库事务里插入业务数据和一条”待发送”的消息记录，然后由定时任务轮询这张表去发消息。

维度 RocketMQ 事务消息 本地消息表
可靠性 高（半消息 + 回查机制） 高（本地事务保证原子性）
实时性 高（消息就绪即可投递） 受轮询间隔影响（通常 1-5 秒）
侵入性 低（只需实现回查接口） 中（需建消息表 + 定时任务）
运维成本 中（依赖 RocketMQ 集群） 低（只依赖数据库）
数据库 I/O 无额外开销 有竞争（业务表 + 消息表同库）

这是微服务解耦最常用的方案，牺牲了实时性，换取高可用和分区容错性。
