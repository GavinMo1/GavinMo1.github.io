Redis数据结构详解

Redis 有五大基础数据类型：String、List、Hash、Set 和 ZSet。这五种类型是正交的，互相不可替代，且构成了完备的数据表达能力：

  • String 对应单一标量
  • List 对应线性序列
  • Hash 对应键值映射
  • Set 对应无序且不重复的集合
  • ZSet 对应带权重的排序集合

为了在内存占用和计算性能之间寻找一个平衡点，Redis 并没有直接将对外暴露的数据类型映射为单一的底层实现，而是采用了多态的设计。每种对象都是由 redisObject 结构体表示，内部通过 encoding 属性决定实际使用哪种底层数据结构。这种设计使得 Redis 可以根据存储数据的数量和类型，动态地进行切换底层数据结构。

String：SDS

适用场景：缓存与简单键值存储。 String 是 Redis 中最常用、最万能的类型。任何只需要存一个值的场景都应该优先考虑它：缓存数据库查询结果（JSON 字符串）、存储 Session Token、用 INCR/DECR 实现计数器（阅读量、点赞数）、用 SETNX 实现分布式锁。如果你拿不准用什么类型，选 String 准没错。

Redis 的 String 类型并没有使用 C 语言原生的字符串，而是设计了一个新的数据类型，叫做简单动态字符串（Simple Dynamic String, SDS）

这个 SDS 内部维护了 len（已用长度）和 alloc（分配总空间）两个字段。

这使得它可以以 O(1) 的时间复杂度获取长度，同时也杜绝了 C 语言原生字符串的缓冲区溢出和二进制安全的问题。因为在 Redis 中修改字符串时，SDS 会预先检查空间是否充足，如果不足，它会进行自动扩容。同时，它会通过长度属性（len）来判断字符串的实际长度，而不是依赖空字符（\0）来判断结尾，这样它就可以安全地存储二进制数据。

而且，SDS 还采用了空间预分配策略和惰性空间释放策略。当字符串增加时，它会分配比实际需要更多的空间，减少了连续追加操作时的内存重分配次数，提高了性能。当字符串缩短时，程序不会立即回收内存，避免缩短后再次追加导致频繁的内存分配。

List：Quicklist

适用场景：队列与时间线。 List 天然适合“有序 + 频繁在两端操作”的场景。用 LPUSH + BRPOP 可以实现一个阻塞消息队列；用 LPUSH + LTRIM 可以实现固定长度的最新动态流（比如保留最近 100 条消息）；LRANGE 可以实现分页展示。如果你的业务需要一个“先进先出”或“最新 N 条”的语义，List 是最直接的选择。

在 Redis 3.2 之后，List 的底层统一从之前的 ZipList 和 LinkedList 换成了 QuickList。

QuickList

QuickList 本质上是一个双向链表，但它的每个节点并不直接存储数据，而是指向一个 ZipList（Redis 7.0 之后替换为 Listpack）。这样做的好处是：

  • 像 LinkedList 一样：节点之间通过 prev/next 指针连接，两端增删都是 $O(1)$。
  • 像 ZipList（Listpack）一样：每个节点内部是一块连续内存，数据紧密排列，没有指针开销，对 CPU Cache 极其友好。

简单来说，QuickList = LinkedList + ZipList（Listpack）。链表负责整体的灵活增删，内部的 ZipList/Listpack 负责紧凑存储。

ZipList

ZipList 是一种为节省内存而设计的顺序型数据结构。由一系列特殊编码的连续内存块组成，没有指针开销。

一个传统的双向链表节点大概长这样：

为了存一个只有 2 字节的单词，要额外花 16 个字节 去存 prev 和 next 指针！而且，链表的节点在内存中是随机散落的，这对 Cache Line 极不友好。

Ziplist 是一个被极其压缩的字节数组。它向操作系统申请一整块连续的内存，把所有的数据挤在一起，内部没有任何指针。

Ziplist 里的一个节点（Entry）由三部分组成：[prevlen] [encoding] [data]

  1. prevlen：记录 上一个节点的总字节数。
  2. encoding：一个变长字段。它的最高几位二进制用于标识数据类型，剩下的二进制位记录当前节点的 data 部分占用的字节数。
  3. data：实际存储的数据内容。

Ziplist 由多个 entry 顺序紧密排布，单个 entry 分为三段：[prevlen] [encoding] [data]

其中 prevlen 是变长字段，且只有两种形态：1 字节或 5 字节。用来保存前一个 entry 的总字节数量，这样就可以实现反向遍历。

解析规则是读取 prevlen 的第一个字节：

  1. 如果首字节的值不等于 0xFF，说明 prevlen 字段仅占用一个字节，字节内就是上一个 entry 的长度。
  2. 如果首字节的值等于 0xFF，说明 prevlen 字段占用五个字节，首字节是标志位，后续四个字节存储长度。

Encoding 也是一个变长字段，它有三种情况，分别是 1、2、5 字节。

可以通过字节高位的标志比特区分编码类型，标识后续 data 存储的是字符串还是整数：

  1. 如果是字符串类型：Encoding 内部会同时记录 data 的字节长度
  2. 如果是整数类型：长度将由编码格式直接确定

解析规则是读取 Encoding 的第一个字节，解析高位标记，以此来判断 Encoding 自身一共占用多少字节，再提取数据相关的信息。

字符串编码：

  • 00xxxxxx → encoding 占 1 字节，低 6 位代表字符串长度
  • 01xxxxxx → encoding 占 2 字节，低 14 位代表字符串长度
  • 10xxxxxx → encoding 占 5 字节，后 4 字节代表字符串长度

整数编码：11xxxxxx → encoding 只占 1 字节，后续没有单独的长度字段。data 长度由编码类型直接确定。

data：根据 encoding 指定的格式保存二进制字符串或者压缩整数。

ZipList 连锁更新问题

上文我们有提到，prevlen 是一个变长字段，它的变长规则与上一个 entry 的总字节数量相关：

  1. 如果前一个节点的大小小于 254 字节，prevlen 整体只占 1 个字节；
  2. 如果大于等于 254 字节，prevlen 就必须扩容到 5 个字节。

这就会带来一个问题。如果你的 ziplist 里有连续的多个节点（比如 e1、e2、e3），它们每个节点的总大小刚好都是 253 字节。因为 253 小于 254，所以从 e2 开始，它们的 prevlen 都是 1 字节，大家都相安无事。

突然，我要在 ziplist 的头部插入一个新节点 e0，大小是 254 或者 255 字节。那么问题就来了：

e1 发现前面的节点变成了 255 字节（大于等于 254 字节），它的 prevlen 需要从 1 字节扩容到 5 字节。这就会导致 e1 的大小从原来的 253 字节变成了 257 字节，增长了 4 个字节。

而 e1 增长到 257 字节后，又会导致后面的 e2 产生相同的变化（因为 257 同样大于等于 254 字节，e2 的 prevlen 也需要扩容）。如此往复，会引发连锁反应，一个节点的插入导致后续所有的节点全部被迫扩大容量。

而且，因为 ziplist 是一块连续内存，所以哪怕只需要扩大 4 个字节，Redis 也必须向操作系统重新申请一块更大的内存，并将所有数据拷贝过去。这会导致这一次的插入操作，性能从 O(1) 直接暴跌到 O(N^2)。

这就是 ziplist 的连锁更新问题。

Listpack

由于连锁更新过于致命，Redis 7.0 废弃了 Ziplist，替换为 Listpack。

Listpack 的设计目标非常明确：在保持 Ziplist 省内存的前提下，消灭连锁更新。

Listpack 中 Entry 的结构变更为：[encoding] [data] [backlen]

  1. encoding：当前节点的编码类型（是字符串还是整数）。
  2. data：当前节点的实际数据。
  3. backlen (Back Length)：记录 当前节点的 encoding 自身大小 + data 大小之和。（注意：它不包含 backlen 自身的大小）。

第一个变成了 encoding，依然是变长字段，但状态更多，主要是一字节为主。

作用仍然是标记后面的 data 的数据类型：

  1. 如果是字符串类型，那么它会在里面附带记录上字符串长度
  2. 如果是小整数，那么甚至可以直接将数值塞进 encoding 内部，不需要使用到 data 区域

第二个是 data，实际存储的数据，基本上没什么区别。值得一提的是，因为 encoding 里面记录了它的长度，所以说它是二进制安全的，可以存放任意字节。

第三个是 Listpack 的核心，引入了 backlen。保存 encoding 和 data 这两部分一共占用了多少字节。而且，backlen 采用了一种特殊的从右向左解析的多字节变长编码。

每个字节的最高位是标志位：

  • 1：表示右边还有属于 backlen 的字节。
  • 0：表示这是 backlen 的最后一个字节（物理内存上的最右侧字节，也是反向遍历的起始读取点）。

通过这样巧妙的最高位设计，Listpack 同时兼顾了正向遍历和反向遍历。

Hash：Listpack->Dict

适用场景：结构化对象存储。 Hash 专门用来存储“一个实体的多个字段”。比如一个用户有 name、age、email 等多个属性，如果用 String 存，你只能把整个对象序列化成一个 JSON，改一个字段就要读写整个值；用 Hash 存，每个字段独立可读写（HGET/HSET），内存效率更高。常见用法：用户信息缓存、商品详情、配置项集合。当你有一组相关的 key-value 需要作为一个整体管理时，选 Hash。

当一个 Hash 对象包含的键值对极少（默认小于 512 个），且所有的键和值的字符串长度都很短（默认小于 64 字节）时，Redis 会使用 Listpack 来充当 Hash（以前是 ziplist）。

一个哈希对象包含的键值对极少（默认小于 128 个），且所有的键和值的字符串长度都很短（默认小于 64 字节）时，Redis 会使用 Listpack 来充当哈希（Redis 7.0 之前使用的是 ziplist）。

虽然 Listpack 是线性结构，但是 Redis 采用了一个非常简单粗暴的设计，将其当做 Hash 来使用。

Redis 直接把哈希的 key 和 value 做成两个连续的节点，紧挨着塞进 Listpack 中。

非常简单粗暴：Redis 直接把 Hash 的 Key 和 Value 作为两个连续的节点，紧挨着塞进 Listpack 中。

物理内存长这样：[Key1] [Value1] [Key2] [Value2] [Key3] [Value3] ...

查询的时候，就是遍历 Listpack，每次跳过两个节点，比较当前节点的 key 是否匹配，匹配则取下一个节点的值。

虽然这样是 O(N) 的复杂度，但是因为数据量很小，而且 Listpack 是一块连续内存，CPU 缓存命中率很高，一般情况下它的速度不亚于计算哈希值去查哈希表。

这样做的好处是没有任何指针开销，非常省内存，而且也没有复杂的哈希冲突处理逻辑。

当数据量突破了上述阈值的时候，Hash 会发生底层编码的转换，蜕变为字典（Dict）。

Dict

Dict 并不是一个孤立的哈希表（hash table），而是由两个哈希表以及一个指针组成。

为什么要用两个哈希表呢？

因为传统的哈希表在扩容时，会申请一块更大的新数组，然后把老数组里的所有数据重新计算哈希并搬运过去。但 Redis 不能这么干，因为 Redis 是单线程的。如果你的数据量比较大，一次性搬运可能需要耗费数秒钟的时间。在这几秒钟内，整个 Redis 都将处于假死状态，任何其他的命令都无法执行。

所以，Redis 通过 Dict 这个特殊的结构体维护了两个哈希表，以及一个索引变量 rehashidx。利用这个特殊的结构，Redis 将整个 rehash 过程分散到多次客户端请求的处理和定时任务中。

  • ht[0]：0 号哈希表是正常服务期间的主存储空间。
  • ht[1]：1 号仅在 rehash 开始时才会被分配内存。
  • rehashidx：进度游标。-1 表示当前未进行 rehash。>=0 表示 rehash 正在进行，数值代表所指向哈希表中正在迁移的桶索引。

当哈希表的负载因子（load factor = ht[0].used / ht[0].size）超过阈值（默认为 1）时，Redis 会触发 Rehash。

扩容过程：

  1. 为 ht[1] 分配足够大的空间（通常是 ht[0] 当前容量的 $2^n$ 倍）。将 rehashidx 设置为 0。
  2. 在此期间，每次对该 Hash 执行 HADD、HDEL、HGET 等命令时，Redis 除了执行本来要做的操作，还会顺手把 ht[0] 在 rehashidx 索引位置上的所有键值对，搬运到 ht[1] 中。搬完后，rehashidx 加 1。如果服务器很闲，没人来访问这个 Hash。Redis 的后台定时任务 serverCron（每秒执行 10 次）会主动介入，每次给它 1 毫秒的时间去搬运。
  3. 当 ht[0] 的所有数据都被搬空后，释放 ht[0]，将 ht[1] 重命名为 ht[0]，并把 rehashidx 重置为 -1。

值得一提的是，这两个哈希表并不会轮流充当新旧表，而是在搬运完之后，直接将指针的指向进行一个交换，永远都是 ht[0] 作为存储的主要空间。

搬运期间的读写规则：

  • 查、删、改：先去 ht[0] 找，找不到再去 ht[1] 找。
  • 增：所有的新增数据，直接写入 ht[1]。保证了 ht[0] 里的数据只会越来越少。

单个的哈希表就是一个经典的桶数组，每一个桶（slot）它是一个链表头。当多个 key 被哈希到同一个位置的时候，它们通过链表串在一起。

Set：Intset->Dict

适用场景：去重与集合运算。 Set 的核心能力是“不重复 + 集合运算”。用 SADD + SMEMBERS 管理标签系统；用 SINTER 求两个用户的共同关注；用 SDIFF 找出 A 关注了但 B 没关注的人；用 SRANDMEMBER 随机抽取幸运用户。如果你的场景需要“保证唯一性”或者需要做交集、并集、差集运算，Set 是唯一正确的选择。

Set 同样有两种形态：Intset 和 Dict。

如果往 set 里存的都是数字，并且数量不多，那么 Redis 就会采用 Intset 这个特殊的结构，以达到节省内存的目的。

Intset 内部没有哈希表，它就是一个严格递增排序的连续的整数数组。

因为数组是严格递增的，所以对于查找，Redis 直接采用二分查找，时间复杂度是 O(log N) 级别。

同时，Intset 支持动态升级。假如一开始存的都是一些小数字（例如 1, 2, 3），它们用 16 位整数、两字节就能够装下，所以 Encoding 会被设为 16 位，数组里每个元素只占两字节。

但是，如果你突然往里面新增了一个超出 32 位范围的大数字，Redis 就会触发数组升级：

  1. 将 Encoding 修改为 int64_t（8 个字节）
  2. 按照 8 个字节的大小重新计算并分配整个数组的内存
  3. 将原来两字节的旧数据在内存中从后往前移动，扩展为 8 个字节
  4. 最后把新来的超大数字放到末尾

需要注意的是，Intset 只支持升级，不支持降级。即使后来你把那个大数字删了，数组依然会保持 8 字节的步长。

当满足下面两个条件之一的时候，set 的底层数据结构会从 Intset 转换为 Dict：

  1. 试图插入一个非数字的字符串
  2. 集合中的元素数量超过了阈值（默认是 512 个）

当使用 Dict 的时候，Dict 的 key 会存储 set 的元素，而 value 会全部指向 NULL。

ZSet：Listpack->Dict + Skiplist

适用场景：排行榜与优先队列。 ZSet 的核心能力是“带权重的有序集合”。用 ZADD + ZREVRANGE 实现实时排行榜（比如按在线时长排名）；用 ZRANGEBYSCORE 实现延迟队列（Score 存截止时间戳，取到期任务）；用 ZINCRBY 动态更新权重。任何需要“按某个指标排序 + 取 Top N / 取区间”的场景，ZSet 都是最优解。

ZSet 既要支持通过 Member 快速找到 Score，又要支持按照 Score 进行范围排序。这两个需求在单一数据结构中很难同时高效满足，因此 ZSet 采用了双结构并存的架构：Dict + Skiplist。

老规矩，数据量小的时候，ZSET 使用 Listpack。

物理布局长这样：[Member1] [Score1] [Member2] [Score2] ...

不过需要注意一个细节，就是此时 Listpack 内部会严格按照 score 从小到大的顺序来维护。这意味着每次插入新元素的时候，Redis 需要遍历 Listpack 来找到正确的排序位置，然后把后面的数据整体后移。这本质上是一个 O(N) 的插入操作，不过因为数据量极小，这块连续内存的拷贝可以在瞬间完成，完全可以接受。

ZSCORE 查询的时候，需要遍历 Listpack，每次跳过两个节点，逐个比较 member 是否匹配。虽然是 O(N) 的复杂度，但在小数据量下，并且因为连续内存的 CPU 缓存命中率极高，速度并不慢。

ZRANGE 范围查询的时候就更加简单了，，因为 Listpack 已经按 Score 排好序了，Redis 只需要遍历到起始位置，然后沿着物理顺序依次取出节点即可。

当元素数量突破阈值，Listpack 的 $O(N)$ 查找就成了瓶颈。

Redis 需要同时满足两种截然不同的访问方式：

  1. 点查：给定 member 找它的 score，这需要一个哈希表。
  2. 范围查找：按 score 区间取数据，这需要数据按 score 排好序。

单一结构无法同时高效满足两者，所以 Redis 的方案是：两个都建，各司其职。

当 ZSet 底层转换为 dict 加 Skiplist 的时候，内存中会同时存在两个结构：

  1. dict：以 member 为 key 的哈希表
  2. Skiplist：按 score 排序的多层链表

两者在底层共享同一组 member 和 score 对象的内存地址，这样可以避免产生数据冗余。

Skiplist

跳表（Skiplist）是一种基于概率统计的随机化数据结构，在链表基础上增加了多级索引。它是一种典型的”以空间换时间”的多层链表结构。

核心特点：

  • 最底层包含所有元素，上层链表是下层的索引
  • 每个节点包含指向前驱、后继的指针，以及多层级的 “跳跃” 指针
  • 平均查找复杂度为 O(log N)，媲美平衡树
  • 相比平衡树，实现更简单，且支持高效的范围查询

概率平衡机制：不同于 AVL 树或红黑树通过旋转来维持严格平衡，跳表通过 “抛硬币” 的方式决定新节点的层数。

  1. 设定概率 $p$（常用 $p=0.5$）
  2. 层高规则：
    • 初始层数 = 1
    • 每次抛硬币，50% 概率层数 +1，直到失败或达到最大限制层高

这种随机性在宏观上能保证查询效率接近 O(log N)。

为什么是跳表，而不是红黑树或 B+ 树？

antirez 亲自在邮件列表中给出了选择跳表的三个原因：

  1. 内存灵活性：一棵红黑树，每个节点必须强绑定 2 个指针（左子树、右子树），有时候还需要父节点指针。而在 Redis 的跳表实现中，节点晋升到高层的概率 $p=1/4$。用数学期望可以算出一个跳表节点平均只包含 1.33 个指针！这比红黑树省了大量指针内存。
  2. 高效的的范围查询：假设你要查排行榜第 50 名到 100 名的玩家。如果用红黑树，你找到第 50 名后，接下来需要在一棵复杂的树形结构里不断进行 中序遍历，指针忽上忽下，对 CPU 缓存极度不友好。而跳表的最底层，就是一条完美的 有序双向链表！找到第 50 名后，你只需要沿着底层的 next 指针“无脑”往后顺藤摸瓜即可，极其畅快。
  3. 实现简单：红黑树的插入和删除，伴随着令人抓狂的“左旋”、“右旋”和“颜色翻转”，稍有不慎就有 Bug。而跳表的插入，只需要调用一下随机函数 random() 决定层数，然后像修改普通链表一样改几个指针即可。跳表的 C 语言代码行数远低于红黑树，这非常符合 Redis “Keep It Simple” 的核心哲学。
